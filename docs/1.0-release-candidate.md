# ModernORM 1.0 candidate and upgrade guide

ModernORM and ModernORMBundle ship as matching `1.0.0-rc.2` prereleases.

```sh
composer require andreybolonin/modernorm:1.0.0-rc.2 andreybolonin/modernorm-bundle:1.0.0-rc.2 --with-all-dependencies
```

The earlier `1.0.0-rc.1` tags identify Core `54308bf` and Bundle `fd5eb69`. Use the migration notes below when upgrading that pair.

## Public API for 1.0

The stable 1.x contract covers the documented behavior of these entry points.

| Entry point | Contract |
| --- | --- |
| Configuration and mapping | Documented options, attributes, connection-scoped DBAL types and supported relations |
| EntityManager and repositories | Persistence, queries, identity, lifecycle, transactions and failure recovery |
| SQL and bulk APIs | QueryBuilder, result mapping, association queries, pagination, bulk writes and explicit context policies |
| Caching and Statistics | Documented cache facade, invalidation, counters, snapshots and operation observers |
| Schema and Symfony | SchemaTool SQL generation and the documented bundle configuration, services and CLI commands |

Public compatibility follows SemVer once 1.0.0 is published. A behavior documented as bounded remains subject to its stated limits. Metadata serialization and internal persister, hydrator and UnitOfWork methods are implementation details. [Compatibility matrix](compatibility.md) · [Mapping scope](mapping-scope.md) · [Write and recovery contract](lifecycle-contract.md)

Manage STORED generated columns and partial unique indexes in SQL migrations. Existing `Index(options: ['where' => ...])` mappings remain available. Use explicit migrations for changes to managed constraint definitions and when generated DDL would remove a protected asset. Changes to a managed trigger function require an explicit rollback migration. [Schema contract](mapping-scope.md#postgresql-exclusion-constraints-and-migration-managed-assets)

## Upgrade from beta

1. Review the [core changelog](../CHANGELOG.md) and existing mapping changes before deploying.
2. Invalidate or version metadata and query-plan caches. The candidate uses metadata cache format V19. Restart workers and coordinate any shared entity L2 cache namespace change with the rollout.
3. Generate a schema diff against a copy of the existing PostgreSQL database. Review the migration and provision required extensions or externally managed trigger functions. Apply it and verify an empty repeat diff.
4. Run application smoke tests for persisted entities and configured cache adapters before rolling out.

Applications upgrading from `1.0.0-rc.1` should move SQL expressions declared with `Column(generated: ...)` and partial unique indexes declared with `Index(where: ..., unique: true)` into explicit SQL migrations. For readback, map a computed field with `insertable: false, updatable: false` and omit the field from bulk write input. [Mapping guide](mapping-scope.md#postgresql-exclusion-constraints-and-migration-managed-assets)

## Candidate verification

Core `910c9c0` and Bundle `1aad19b` passed their GitHub Actions matrices. Core verified PHP 8.4–8.6 and PostgreSQL 17–19 with locked, lowest and latest allowed dependencies. The bundle verified the same PHP and PostgreSQL range, Symfony 7.4 and 8.x, and migrations on Doctrine Migrations 3.9.1 and 3.9.9. [Core CI](https://github.com/andreybolonin/modernorm/actions/runs/45357610526) · [Bundle CI](https://github.com/andreybolonin/modernormbundle/actions/runs/45359346697)

Fresh Symfony 7.4 and 8.1 applications installed both candidate ZIPs without development dependencies on PHP 8.5.13 and PostgreSQL 18.7. Each booted the production container, warmed its cache, applied a generated migration and returned an empty repeat diff. PostgreSQL enforced the declared CHECK.

## Release gates

- Verify CI and both package distributions against the release commits.
- After publishing the RCs, repeat the clean install and beta-to-RC upgrade with Packagist as the sole package source. Exercise the RC in a representative application where feasible.
- Review migration and rollback plans, release notes, package contents and licenses before tagging stable.
